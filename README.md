## 🎮 게임 흐름

1. **로그인** — Google 계정이나 이메일로 로그인하고 닉네임을 정합니다.
2. **검 강화** — 골드로 검을 강화합니다. 성공하면 한 단계 오르고, 실패하면 검이 파괴되어 처음으로 돌아갑니다. 높은 단계의 검은 팔아서 골드를 얻습니다.
3. **아티팩트** — 상점과 가챠에서 아티팩트를 얻고, 재료를 모아 강화한 뒤 3개 슬롯에 장착합니다.
4. **전투** — 검과 아티팩트로 정해진 전투력으로 스테이지를 자동 전투로 공략하고 보상을 받습니다.
5. **경쟁과 소통** — 검 최고 단계 · 스테이지 · 전투력 랭킹으로 경쟁하고, 전체 채팅과 강화 공지로 소식을 나눕니다.

<br>

## ✨ 주요 기능

### 🔐 로그인과 계정
- 이메일 회원가입 · 로그인과 **Google 로그인** 지원 (클라이언트가 받은 ID 토큰을 서버가 검증)
- 로그인 후 발급된 **JWT**로 모든 API 인증, 채팅(STOMP)은 최초 연결 시 한 번만 토큰 확인
- **자동 로그인**: 리프레시 토큰을 **Android Keystore**로 암호화해 기기에 저장 (1인 1기기)
- 첫 로그인 시 닉네임(공백 없이 1~10자, 중복 불가) 설정 후 첫 단계 검 · 초기 골드 · 시작 아티팩트 지급

### 🗡️ 검 강화와 판매
- 단계별로 정해진 성공 확률과 골드 비용으로 강화 — 성공 시 +1단계, 실패 시 파괴되어 첫 단계로
- 첫 단계가 아닌 검은 단계별 판매가만큼 골드를 받고 판매 (높게 올릴수록 위험도 보상도 커지는 구조)
- 클라이언트가 보낸 현재 단계(`expectedLevel`)가 서버와 다르면 거절해 화면 · 서버 상태 불일치 방지
- 높은 단계 강화 성공 시 전체 공지 및 랭킹 반영

### 💎 아티팩트
- 상점 · 가챠 · 전투 보상으로 획득, 중복 획득 시 강화 재료로 누적
- 등급 · 레벨별 재료와 골드로 강화 (등급마다 최고 레벨 상이)
- 3개 슬롯에 장착 · 해제 · 이동
- 치명타율 · 흡혈 · 최대 체력 · 공격 속도 등 복수 능력치 보유, 레벨에 따라 상승

### ⚔️ 전투
- 검과 장착 아티팩트로 계산한 능력치로 적과 **자동 전투** (일반 / 보스 스테이지별 시간 제한)
- **클라이언트 · 서버 교차 검증**: 서버가 내려준 시드와 직접 구현한 난수 생성기 **SplitMix64**로 양쪽이 같은 전투를 계산하고, 보고 결과가 일치할 때만 보상 지급
- 진행 중인 전투는 서버 Redis 세션에 저장되어 앱을 다시 켜도 **이어하기** 가능
- 배속, 처치 · 패배 · 보스 경고 연출, 결과 팝업 · 재도전

### 🛒 상점과 가챠
- 골드 · 다이아 · 무료 상품 구매 (재화 차감 · 보상 지급 · 구매 기록을 한 트랜잭션으로 처리)
- 가중치 추첨 / 등급 추첨 두 가지 가챠, 최대 10연차
- 같은 `requestId`로 재전송하면 처음 결과를 돌려줘 **중복 결제 방지**
- 나무 · 금 상자가 열리는 애니메이션과 광선 연출

### 🏆 랭킹
- 검 최고 단계 · 최고 클리어 스테이지 · 현재 전투력 3종
- 상위 100명은 매일 01:00(KST) 집계 결과, 내 정보는 방금 세운 기록까지 반영한 예상 순위 표시
- 동점이면 먼저 달성한 플레이어가 앞섬

### 💬 채팅과 공지
- 로비에서 전체 플레이어와 실시간 채팅 (STOMP, 끊김 시 자동 재연결)
- 관리자 공지와 강화 성공 공지를 상단 공지 띠로 표시

#### 운영 Flyway 검증 실패
- **문제**: 병합된 마이그레이션 파일의 버전이 develop의 최신 버전보다 작아 운영에서 Flyway validate가 실패
- **해결**: 파일 버전을 바로잡고, 파일명을 작성 시점 기준 `VyyyyMMdd_HHmm__설명.sql`로 통일하는 규칙 수립

#### 헬스체크 경로 변경 시 전체 서버가 Unhealthy
- **문제**: 헬스체크 경로가 인증 필터에 막히면 401이 나와 모든 서버가 Unhealthy가 되고 교체가 반복될 수 있음
- **해결**: 새 경로 허용 코드 배포 → 새 경로 200 확인 → 대상 그룹 경로 변경 순서로 바꾸고, 헬스체크는 외부 의존성이 빠진 readiness로 결정

#### 등급 랜덤 가챠가 의도치 않게 동작
- **문제**: 항목을 직접 지정한 가챠 행에도 등급 검사가 적용되어 결과가 의도와 달라짐
- **해결**: 등급 검사는 보상 코드가 빈 등급 랜덤 행에만 적용하고, 지정 행의 등급은 참고용으로만 사용

<summary><b>👤 김우진</b> — 클라이언트 · PM</summary>

#### Domain Reload가 꺼져 이전 플레이의 정적 상태가 남는 문제
- **증상**: 로비 씬에서 바로 실행하면 `BaseUrl`이 비어 요청 실패, 이전 토큰이 남아 첫 로그인이 "로그인 만료"로 처리
- **원인**: Enter Play Mode 설정에서 Domain Reload가 꺼져 있어 static 값이 다음 플레이까지 남음. 토큰(`AuthJwtToken`)과 유저(`GameSession`)도 따로 살아 있었음
- **해결**: `RuntimeInitializeOnLoadMethod`로 시작 시 초기화, 토큰을 `GameSession`(DontDestroyOnLoad 싱글턴)으로 통합

#### 서버 검증 응답이 처치 연출보다 먼저 와서 연출이 사라지는 문제
- **증상**: 한 방에 처치되는 적을 치면 체력바가 줄지 않고 바로 다음 적으로 넘어가거나, 검이 닿기 전에 적이 사라짐
- **원인**: 피격 반응을 검이 닿는 시점(0.22초)으로 늦췄는데 서버 응답이 먼저 도착해 다음 세부 스테이지가 시작되며 연출이 취소됨
- **해결**: `BattleManager`가 다음 세부 스테이지로 넘어가기 전 연출(`NextSubStageTransition`)이 끝나기를 기다리게 하고, 처치 · 다음 적 등장 · 재개를 하나의 연출로 묶음
- **검증**: 매 프레임 기록 — 1배속 2.28초, 2배속 1.14초로 시안 값과 일치

#### 토큰 만료 시 여러 요청이 동시에 401을 받는 문제
- **증상**: 토큰 유효 시간 1시간이 지나면 상점 구매가 아무 안내 없이 계속 실패
- **해결**: `HttpErrorHandler`가 401을 세션 만료로 보고 로그인 화면으로 이동, 동시에 401을 받아도 이동이 한 번만 일어나도록 `IsExpired` 플래그 도입
- **검증**: 목 서버로 만료된 요청 2개를 동시에 보내 확인

#### 강화 결과 공지가 강화 연출보다 먼저 보이는 문제
- **원인**: 서버 `SwordService`가 응답을 보내기 전에 WebSocket 공지를 먼저 보냄

<summary><b>👤 오수호</b> — 서버 · 클라이언트</summary>

#### 전투 구조 변경과 클라이언트 · 서버 계산 결과 불일치
- **배경**: 처음에는 서버가 전투 전체를 한 번에 계산하고 이벤트 로그를 내려주면 클라이언트는 재생만 하는 구조. 조작 여지는 없지만 배속 · 전투 중 상호작용 · 중간 포기 · 재접속 같은 기능으로 확장할 수 없었음
- **구조 변경**: 클라이언트가 세부 스테이지 전투를 실시간으로 계산 · 표시하고 결과를 보고 → 서버가 같은 조건으로 재계산해 검증. 유저마다 Redis 전투 세션 하나(동시 전투 방지 락 역할), 보상은 세션에 쌓았다가 전투 종료 시 한 번에 반영
- **문제**: 검증이 성립하려면 같은 시드에서 클라이언트와 서버가 항상 같은 치명타 · 피해량을 내야 하는데, C# `System.Random`은 Java와 구현이 달라 Mono(에디터) · IL2CPP(Android) · Java(서버) 간 결과를 보장할 수 없음 → 정상 유저도 검증 실패로 패배 처리될 위험
- **해결**
  - 정수 덧셈 · 시프트 · XOR · 곱셈만 쓰는 **SplitMix64**를 직접 구현하고 `unchecked`로 감싸 런타임 · 오버플로 설정에 따른 차이 제거
  - `NextDouble`은 상위 53비트를 정수로 꺼낸 뒤 곱셈 한 번으로 변환, `NextInt`는 범위를 넘는 값을 버리고 다시 뽑아 치우침 제거
  - 서버가 전투 시작 시 `battleSeed`를 내려주고, 세부 스테이지마다 `Mix(battleSeed + subStageIndex)`로 독립 난수 생성기를 만들어 재접속 · 부분 검증 시에도 난수 순서가 어긋나지 않게 함
- **결과**: 시드 0의 첫 값이 원본 기준값(`E220A8397B1DCDAF`)과 일치, 프레임 단위 진행 결과와 `RunToEnd()` 결과 일치 확인

#### 부동소수점 오차로 전투가 끝나지 않는 문제 (클라이언트)
- **문제**: 플레이 테스트 중 가끔 세부 스테이지가 끝나지 않고, 제한 시간이 지나도 시간 초과 처리 없이 멈춤
- **원인**: n번째 공격 시각 `n × (1 / 공격속도)`의 부동소수점 오차 (예: 공격 속도 2.3, 69번째 공격 → `30.000000000000004`). 제한 시간 비교에는 `TimeEpsilon` 보정이 있었지만 경과 시각 비교(`time > Elapsed`)에는 없어 공격도 시간 초과도 일어나지 않는 상태가 됨 → 서버 `RunToEnd()`에서는 무한 루프로 검증 스레드가 돌아오지 못할 위험
- **해결**: `TimeEpsilon = 1e-9`를 전투 규칙 상수로 두고 `time > Elapsed + TimeEpsilon`처럼 모든 시각 비교에 같은 기준 적용, "같은 시각이면 플레이어 선공" 규칙에도 동일 허용 오차 적용

#### 전투 보고를 다시 보내면 결과가 달라지거나 실패하는 문제 — 멱등성 (서버)
- **문제**: 응답 유실 후 재전송 시 번호 불일치로 패배 처리, 전투 종료 후 재요청 시 다른 결과 반환, 처리 중 두 번째 요청이 유저 락과 충돌해 실패
- **원인**: 보고 요청이 멱등하지 않았고, 클라이언트는 실패 종류(거절 / 결과 불명 / 처리 중)를 구분하지 않음
- **해결 (서버)**
  - 진행 중 전투: Redis 세션에 직전 보고(`subStageIndex`)와 응답을 저장, 같은 보고는 재검증 없이 저장된 응답 반환
  - 끝난 전투: 종료 결과를 `battle:end:{battleId}`로 10분 보관해 마지막 보고 · 포기 · 검증 실패 재요청에 같은 결과 반환
  - 최종 방어선: `battle_histories`의 `battle_id` 유니크 제약으로 중복 정산 차단
  - 유저 단위 락(`battle:lock:{userId}`, 5초)은 토큰으로 소유를 확인해 해제하고, 락 충돌 시 `REQUEST_IN_PROGRESS`로 응답
- **해결 (클라이언트)**
  - 결과 불명 실패와 `REQUEST_IN_PROGRESS`는 1초 뒤 같은 요청 재전송 (최대 3회)
  - `VERIFY_FAILED`, `BATTLE_ID_MISMATCH` 등 거절은 재시도 없이 서버 문구 팝업 표시, 401은 `HttpErrorHandler`가 로그인 화면으로 이동
  - 전투 포기 · 씬 이탈 후 늦게 온 응답은 무시
- **결과**: 같은 보고를 두 번 보내도 같은 응답 · 세션 한 칸만 진행, 골드 중복 지급 없음, HP 조작 보고는 그대로 `VERIFY_FAILED`
</details>

#### Flyway 도입 후 "테이블이 이미 있음" 오류
- **문제**: `ddl-auto=update`로 만들어진 로컬 테이블 때문에 Flyway의 `CREATE TABLE` 실패
- **해결**: 로컬 DB를 지우고 Flyway로 재생성, Redis 랭킹도 함께 비워 DB와 맞춤. 이후 `ddl-auto`는 `validate`로 통일

#### Redis 통합 테스트만 실패
- **문제**: `@DataRedisTest`에서 "JPA metamodel must not be empty" 오류
- **원인**: 메인 클래스의 `@EnableJpaAuditing`을 JPA가 없는 테스트에서도 읽음
- **해결**: 별도 설정 클래스(`JpaConfig`)로 분리

#### 비용이 0인 단계에서 500 오류
- **문제**: 시트 검증은 강화 비용 · 판매가 0을 허용하는데, 재화 서비스는 0을 코드 오류로 보고 500 반환
- **해결**: 재화 서비스에서 0은 "변동 없음"으로 처리하고 음수만 오류로 유지, 0이 의미상 불가능한 칸은 시트 검증에서 차단

#### AWS 환경 랭킹 미표시 (Redis CROSSSLOT)

- **해결**: 랭킹 키에 해시 태그(`ranking:{TYPE}`)를 적용해 실시간 · 집계본 · 집계 시각 키를 같은 슬롯에 배정
